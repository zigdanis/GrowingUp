Image Capture Redesign

ChatGPT-style photo & camera picker for the two fixed person-image slots — replacing the legacy 2015-era WDImagePicker / WDImageCropViewController.

1 Overview & scope

Recreate ChatGPT's image-upload feel for the existing two fixed image slots in the EditPerson scene:

Main (app) pictureRectangular crop, shown full-screen in PersonOverview.
Widget pictureCircular avatar, shown in the home-screen widget and picker buttons.

Each slot tap opens one full-screen SwiftUI flow (hosted into UIKit via UIHostingController, .fullScreen) that yields exactly one image from either a custom PhotoKit grid (PR1) or an inline in-app camera card (PR2), which is then cropped, downsized, confirmed, and set into the slot. No multi-image selection.

SwiftUI-first for all new code. The legacy WDImagePicker + WDImageCropViewController stack is ripped out. PR scope is strictly the image-pick flow.

2 Flow — identical shape for both slots

  • Tap slot → full-screen sheet (UIHostingController, .fullScreen)
  • ImageCaptureFlowView → pick one image (custom grid in PR1, + camera tile in PR2)
  • Tap a photo → straight to crop (no intermediate preview/confirm screen)
  • Use → downsize (per-slot target) → set slot → dismiss

Single-select throughout. The crop seam (CropStep) takes (source image + slot shape) in and returns a cropped image out, so the crop implementation can be swapped without rippling through the flow.

Square widget output (circle as a display-time mask, not a baked transparent PNG) is what kills the transparent-PNG → JPEG black-corner bug: the stored file is a full opaque square, masked to a circle only when displayed.

4 Decisions — every question, every answer

The full design tree, walked one branch at a time. Each card is a question that was asked, the option chosen, and why.

PR1 · Q1

How should the main (app) picture be cropped and displayed?

aspectFill + fixed 4:5

Crop to a locked 4:5 portrait and display with scaleAspectFill in PersonOverview. Fills the full-screen frame with no white letterbox (the previous scaleAspectFit + 3:4 combo letterboxed).

PR1 · Q2

How should the widget picture be cropped and stored?

Circle mask, square output

Circular mask during crop for the avatar feel, but persist a square opaque image (cropImageCircular = false). The circle is re-applied at display time, avoiding alpha being flattened to black corners by JPEG encoding.

PR1 · Q3

Where and how should images be downsized before saving?

Downsize crop in-flow, per slot

Downsize inside the capture flow, keyed off the slot's CropShape (1800px main / 480px widget), before building PersonImage. Avoids storing full-resolution JPEGs (q=1) for images shown at 56pt.

PR1 · Q4

After tapping a photo, what happens next?

Tap → straight to crop

No intermediate "preview / confirm" screen. A tap loads the full-resolution asset and goes directly into the crop step; the crop's own Use/Cancel is the confirmation.

PR1 · Q5

How should photo-library permission be requested?

Direct system prompt

Go straight to the OS permission prompt on first entry (no custom pre-ask wall). Graceful degradation handles full → limited; denied/restricted states get the explainer view with a Settings deep-link.

PR1 · Q6

How should full-resolution selection loading behave (iCloud, errors)?

Resilient: error + progress + cancel

Use progressHandler for a determinate progress UI during iCloud downloads, keep the PHImageRequestID so the load is cancellable, and on nil/error clear the spinner + show "Couldn't load photo" while staying on the grid. (The first build hung forever on iCloud failure.)

X-cut

Should this work add a way to remove / clear a slot's image?

Add remove affordance

A picker that can set an image but never clear it is incomplete. Add a remove affordance with proper persistence wiring.

Remove · A

How should clearing a slot persist? (Gateway edit() currently deletes nothing.)

Nil in-memory, delete on Save

Tapping ✕ shows the placeholder immediately, but disk/CoreData stay untouched until Save — Cancel/back restores the old image. Needs new delete-task wiring in gateway edit(): when a slot is nil (or replaced) and the person had a stored id, run the delete task. CoreData already nulls the id via populate. Matches how EditPerson defers all persistence to Save; reversible until commit.

Remove · B

What does the remove affordance look like on a filled slot?

✕ badge on filled slot

A small ✕ badge in the top-trailing corner of a filled slot (hidden when empty). Matches ChatGPT attachment + iOS convention; discoverable; the tap target is separate from the re-pick tap on the image body.

Remove · C

Which PR carries the remove affordance?

PR1 (photos)

It touches the same cell / presenter / gateway PR1 already modifies, and a picker that can't undo a wrong pick is an incomplete flow. Ship them together.

PR2 · Q1

How does the user enter the camera?

Camera tile = first grid cell

The camera is the first cell of the photo grid: a glyph that turns into a live preview once permission is granted. Keeps a single entry surface rather than a separate source chooser.

PR2 · Q2

What camera controls, and which camera by default?

Full set, back default

Inline card with shutter / flip / flash (off · auto · on) / close. Back camera is the default; front-camera capture is un-mirrored.

PR2 · Q3

After capture, what is the crop flow?

Reuse crop; cancel = retake

Capture feeds the same CropStep as the photo path. Cancelling the crop returns to the live camera to retake; the camera's own ✕ returns to the grid.

PR2 · Q4

What is the camera permission-denied UI?

Reuse PermissionExplainerView

Reuse the same explainer component as photos, with .cameraNeeded / .cameraDenied / .cameraRestricted configs. Only copy, icon, and action differ.

7 Folded-in fix: replace orphan

Pre-existing bug — now fixed inside PR1

Picking a new image for a person who already had one wrote a new-id file and orphaned the old file on disk (new id ≠ old id). This ships in production today. The PR1 delete-on-save reconcile now also covers it: delete the stored file whenever oldId != parameters.image?.id (covers both clear and replace), so an untouched edit never deletes the file it is about to keep.

// CachePersonsGateway.edit() reconcile, per slot
if let saving = appPicSavingTask(for: parameters)            { tasks.append(saving) }
if let delete = outdatedAppPicDeleteTask(person, parameters) { tasks.append(delete) }
// outdated* returns nil when storedId == parameters.appImage?.id  (unchanged → keep)

8 Execution & orchestration

The two PRs ship one-by-one (PR1 photos, then PR2 camera). Each PR runs through an autonomous build → publish → review → address loop:

  • Orchestrator manages the plan and sequences the PRs.
  • Worker per PR: finalize code, build + test + lint, branch, push, open the GitHub PR, report back.
  • Reviewer per PR: code-review the diff, post the review report as comments on the PR page, report back.
  • Address loop: orchestrator dispatches fixes for raised issues; worker pushes changes; review re-runs.
  • Exit: loop until the reviewer raises no remaining issues, for every PR.

Non-negotiables carried from the repo: commit messages end with the Co-Authored-By trailer; PR bodies end with the Claude Code generated-with line; work happens on feature branches, never directly on master.
